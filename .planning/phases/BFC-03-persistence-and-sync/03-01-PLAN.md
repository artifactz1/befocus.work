## Phase Goal

**As a** person who sets up BeFocus to look the way I like, **I want** my look to still be there
the next time I open the app, on this device or another one I sign in on, **so that** I never redo
it and never see the default flash before my look appears.

(Derived from the ROADMAP Phase 3 goal.)

coalescing saver, and the first-frame paint script builder. Nothing is wired into React yet.

Purpose: SYN-03 (guest storage), SYN-05 (save ordering), ENG-05 (first-frame script), and the
Phase 9 "Guest storage" seam. Keeping these pure makes every rule checkable with `bun run`.
Output: four modules, two check scripts, three call sites moved onto the helper.
</objective>

Create `lib/storage/browser-storage.ts` (RESEARCH Pattern 5):

- `readStored<T>(key: string, schema: ZodType<T>, storage: Pick<Storage, 'getItem'> | undefined =

  defaultStorage()): boolean` writes `JSON.stringify(value)` and returns `true`, or returns `false`
  when storage is missing or `setItem` throws (quota, private mode).

**`guest-look.ts`** (RESEARCH Pattern 6):

- Export `GUEST_THEMES_KEY = 'befocus.themes'`, `GUEST_ACTIVE_KEY = 'befocus.activeThemeId'` and
  `GUEST_PAINT_KEY = 'befocus.lookPaint'`.
- Define the record schema `z.array(z.object({ id: z.string().uuid(), name: z.string().max(80),
  look: lookSchema }))`.
- `readGuestLook(storage?)`: read the active id (`z.string().uuid()`) and the themes, find the
  entry with that id, and return its `look`, or `null` if any step fails.
- `writeGuestLook(look: Look, storage?)`: reuse the active id if a matching entry exists, otherwise
  `crypto.randomUUID()`. Write the themes with that one entry (`name` kept, or `'My look'`), the
  active id, and `lookToTokens(look)` to `GUEST_PAINT_KEY`. Return `true` only if all three writes
  succeed.
- Storage parameters are injectable, matching the helper.

**`look-saver.ts`** (RESEARCH Pattern 7):

`createLookSaver({ send, onSaved, onError }: { send: (look: Look) => Promise<void>, onSaved: (look:
Look) => void, onError: (error: unknown) => void })` returns `{ save(look: Look): void }`.

- Keep one `inFlight` flag and one `pending: Look | null`.
- `save` sets `pending = look` and, if idle, starts the loop. The loop takes `pending`, clears it,
  and awaits `send`, calling `onSaved(sent)` on success or `onError(error)` on failure. It repeats
  while `pending` is set.
- No timers, no retries inside one send (UI-SPEC section 3).

**`look-paint.ts`** (RESEARCH Pattern 4):

- `export type PaintTokens = ReturnType<typeof lookToTokens>`.
- `export function buildPaintScript(tokens: PaintTokens | null): string` returns one self-invoking
  function wrapped in `try { } catch (e) {}`.
- Into the script, serialise:
  - `t`: the tokens, or `null`.
  - `n`: the allowed property names, `Object.keys(lookToTokens(DEFAULT_LOOK).props)`.
  - `p`: `PROGRESS_IDS`.
  - `d`: `DENSITY_IDS`.
  - `k`: `GUEST_PAINT_KEY`.

  Serialise all of them with one `safeJson` helper that runs `JSON.stringify` and then replaces
  `<` with `\u003c` and U+2028 / U+2029 with `\u2028` / `\u2029`.
- At run time:
  - When `t` is `null`, read `t = JSON.parse(localStorage.getItem(k) || 'null')`.
  - Return if `t` is not an object.
  - For each name in `n`, set `document.documentElement.style.setProperty(name, value)` only when
    `typeof value === 'string'`, the value matches `/^[^;{}<>\\]{0,200}$/` and it does not contain
    `url(`.
  - Set `data-progress` and `data-density` only when the value is in `p` / `d`.
  - Never set `data-panel`; the painter owns it.
- Write the script as plain ES5 in a template string, with no build step and no imports at run
  time.

**`persistence.check.ts`** covers:

- (a) guest round trip with a fake storage: `writeGuestLook(look)` then `readGuestLook()` deep
  equals, and the id is stable across two writes.
- (b) `readGuestLook` gives `null` for: no keys, an active id with no match, a theme whose look
  fails `lookSchema` (an extra key), and bad JSON.
- (c) `writeGuestLook` with a throwing `setItem` returns `false`.
- (d) saver ordering with manually resolved promises: `save(A)`, `save(B)`, `save(C)` while A is in
  flight sends `[A, C]` in that order, never two at once. `onSaved` is called with A, then C.
- (e) a failed send calls `onError` once and the next `save` sends again.
- (f) save-back-to-start: `save(B)` while A is in flight, then `save(A)` sends `[A, A]` last, so
  the stored look is A. This is the case comparing with `persisted` would break (03-CONTEXT
  "Save semantics").
- (g) paint script: run `new Function('document', 'localStorage', script)` with fake `document`
  and `localStorage` objects. Then check:
  - With tokens, every property is set.
  - With `null` and a stored cache, the cache is applied.
  - A stored cache holding an unknown name, a `url(` value, a `;` value and `data-progress:
    'evil'` applies none of those.
  - A token value of `'</script><script>alert(1)</script>'` produces a script string with no
    `</script` substring.
  - Throwing storage leaves the fake document untouched and does not throw.
