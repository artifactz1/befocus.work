## Phase Goal

The dashboard receives a signed-in user's saved settings on the server render in production, from
exactly one hydration path, and the styling and lint toolchain is single-sourced and trustworthy again.

<objective>
Slice: a signed-in user sees their own timer values on first paint, from exactly one settings read,
with nothing on the client racing or overwriting it.

Purpose: FND-05 (and the first-paint half of FND-01). Phase 2's customization store copies this
pattern (D-07), so it must be the clean, documented zustand + TanStack App Router pattern.
Chosen mechanism (Claude's discretion under D-07/D-06):
- Timer store: per-request vanilla store created from server props inside a React context provider
  (zustand's documented Next.js pattern). A module singleton cannot work: zustand 5's server snapshot is
  `getInitialState()`, so values set after creation never reach SSR, and a server singleton would leak
  state between requests.
- Query cache: server layout builds a throwaway QueryClient, `setQueryData(['userSettings'], settings)`,
  and passes `dehydrate(...)` to `<HydrationBoundary>`; `useUserSettings` gets `staleTime: Infinity`.
  AppProviders switches to a per-request QueryClient so hydrated user data never lands in a
  server-global cache.
Output: refactored store, layout, providers, save hook; deleted TimerInitializer, DashboardShell, useTimer.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Next server render -> HTML/RSC payload | Per-user settings are serialized into the response |
| server module scope | Anything module-global is shared across all users' requests |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-07 | Information Disclosure | AppProviders module-level QueryClient | mitigate | Create QueryClient inside `useState` so each server request gets its own cache; HydrationBoundary never writes user A's settings into a client shared with user B |
| T-01-08 | Information Disclosure | timer store singleton | mitigate | Store created per provider instance via `useState(() => createTimerStore(...))`; no module-level store instance exists |
| T-01-09 | Information Disclosure | dehydrated settings in RSC payload | accept | Only the requesting user's own non-sensitive timer settings (durations, session count) are serialized, for that user's own response |
| T-01-10 | Tampering | useSaveUserSettings PUT->POST fallback | accept | Both endpoints are auth-gated and user-scoped server-side (`requireAuth`, userId from session); client choice of verb cannot touch another user's row |
</threat_model>
