## Phase Goal

**As a** signed-in person running focus sessions, **I want to** have every block saved to my
account automatically, even through flaky connections, **so that** my history is complete without
me doing anything.

<objective>
Eighth slice: the account recorder. A small persisted queue (merge by id, one request in flight,
chunks of 100) sends records from the store's sink to PUT /user/blocks and keeps them on failure.
Per CONTEXT, a failed write is silent: no toast, queued and retried.

Purpose: BLK-03 / BLK-04 end to end for accounts.
Output: createRecordQueue in block-records.ts with its checks; account mode wiring in the provider.
</objective>

    - push([a]) with send resolving 'ok' calls send once with [a] and leaves the stored queue empty
    - push of 150 records sends two chunks (100, then 50) in order, never two sends at once
    - send 'retry' keeps the chunk in the stored queue and stops; a later flush() sends it again
    - send throwing is treated as 'retry'
    - send 'drop' removes that chunk and continues with the rest
    - push([a]) while a send of [a] is in flight, then push([a2]) with a2.id === a.id: after 'ok' for the first send, the queue still holds a2 and the next send carries a2
    - a queue created on a storage that already holds records sends them on flush()
    - the stored queue never exceeds MAX_STORED_RECORDS (newest kept) and corrupt stored entries are dropped
    - queueKey('u1') is 'befocus.blockQueue.u1'

appends records to an in-memory buffer ref. An effect on userId creates `createRecordQueue({ key:
queueKey(userId), send })`, pushes any buffered records, calls `flush()` (sends what a previous
visit left), sets `sinkRef.current = records => queue.push(records)`, and adds a window 'online'
listener calling flush; cleanup removes the listener and resets the sink to buffering. `send` calls
`api.user.blocks.$put({ json: { records } })`: status 200 gives 'ok'; 400, 413 or 422 gives 'drop';
anything else (401, 5xx) gives 'retry'; a thrown fetch error is 'retry' (the queue catches it).
No toast, no UI (CONTEXT: failed writes are silent). The pagehide handler from 08-06 calls this
same sink, so a block still running or paused at close or reload lands in the stored queue as a
'reset' record and the next load's flush sends it (decision W4); its fetch on pagehide may be cut
off, which is fine because the record stays queued until a send returns 200. If pagehide fires
before the session user id is known (the in-memory buffer), that record is not kept: no block can
have run longer than that first moment of the load. Guest mode is unchanged. Sign-out sites are
not edited: queues are keyed by user id, so another user signing in on this browser never sends
them, and the server's setWhere is the second guard.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-08-28 | Spoofing / Information disclosure | shared browser, two accounts | mitigate | Queue key includes the session user id, so user B's session never sends user A's queue; server setWhere (T-08-22) refuses cross-owner overwrites |
| T-08-29 | Tampering | stored queue | mitigate | Each stored item re-validated with blockRecordSchema on read; invalid dropped; the server validates again |
| T-08-30 | Denial of service | retry loop | mitigate | Single flight, retry only on push / mount / online (no timer loop), chunks of 100, invalid chunks dropped instead of retried |
| T-08-31 | Repudiation | silent failures | accept | Per CONTEXT failures are silent; console.warn on dropped chunks is the only trace, acceptable for personal timing data |
</threat_model>
