Reshape useToDoStore.tsx in place (same file, per CONTEXT "reshaped, not duplicated") into a
per-request store following useTimerStore: `createTasksStore({ mode, tasks })`,
`TasksStoreProvider({ mode: 'guest' | 'account', initialTasks: Task[] | null, children })`,
`useTasksStore(selector)`, `useTasksStoreApi()`. State: `mode`, `tasks: Task[]` (newest first),
`loadState: 'ready' | 'error'`. Pure mutators only (no fetch here): `hydrateTasks(tasks)`,
`insertTask(task)` (prepends), `patchTask(id, patch)`, `replaceTaskId(tempId, id)`,
`dropTask(id)`, `setLoadState(state)`. Remove the old `useTodoStore` export and its
addMode/editMode fields. Per-request (not module-level) because 09-04 seeds it from the server
render; a module store would leak between requests on the server.

useTasks.ts: keep `useUserTasks()` but map rows to the client Task (`id: String(row.id)`, no
editMode). Replace the create/update exports with `useTaskActions()` returning `add(text)`,
`edit(id, text)`, `toggle(id)`, `archive(id)`, `restore(id)`. Text is trimmed; empty is ignored;
longer than TASK_TEXT_MAX is cut to it. Guest mode: mutate the store only, new ids are
`crypto.randomUUID()` (CONTEXT Q9). Account mode: optimistic store change first, then the API
(`api.user.tasks.$post` for add with a temp `crypto.randomUUID()` id swapped via `replaceTaskId`
on success to `String(res.id)`; `api.user.tasks[':id'].$put({ param: { id }, json: patch })` for the
rest); on failure restore the snapshot (dropTask for a failed add, previous fields otherwise) and
`toast.error(\`Couldn't save ${text}. Check your connection and try again.\`)`. While an add is
in flight, later actions on that temp id await the same promise (keep a Map of tempId to promise
inside the hook module) so they hit the server id. `toggle` is the single entry point for ticking;
09-07 routes it through the plan's completeTask so ticks during a live block are recorded.

PrefetchUserTasks.tsx: keep it working for now against the new store (`useTasksStoreApi()
.getState().hydrateTasks(data)`); 09-04 replaces it with server-rendered hydration.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Tampering / XSS | ListTab task rows | mitigate | Text rendered as React text children only; verify gate greps for dangerouslySetInnerHTML in components/tasks |
| T-09-02 | Denial of service | add/edit inputs | mitigate | Client trims and caps at TASK_TEXT_MAX 500 (`maxLength`); server cap added in 09-04 |
| T-09-03 | Elevation | existing PUT /user/tasks/:id | accept | Already scoped by `and(eq(tasks.id), eq(tasks.userId, user.id))`; no route change in this plan |
| T-09-04 | Information disclosure | per-request tasks store | mitigate | Store created per request through TasksStoreProvider, never module-level, so one user's tasks cannot leak into another server render |
</threat_model>
