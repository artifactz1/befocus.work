Planner's root-cause hypotheses (Task 1 must confirm or replace them with what the browser shows):
H1 (comes back): after a successful DELETE, `deleteSound(id)` changes `sounds`, the GlobalSoundsPlayer
merge effect re-runs with the still-stale `userSounds` cache that contains the id, and re-adds it.
After the refetch the add-only merge never removes it, so it stays visible until a full reload.
H2 (cannot delete): starters are marked `isCustom: true`, get a Delete button, and DELETE
`/user/sounds/jazz` returns 404 because starters are not rows. Even a local removal would be undone on
refresh because starters are re-seeded at module load.
H3 (guest): guests get a 401 on delete and on the list GET.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser -> DELETE /user/sounds/:id | Untrusted id from the client; must only affect the session user's rows |
| localStorage -> store | `befocus.hiddenStarters` is user-writable; parsed as untrusted JSON |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Elevation of privilege | deleteUserSound handler | mitigate | Delete statement itself filters `and(id, userId)` and 404s on zero returned rows (not only the pre-check); verified by scenario E curl |
| T-07-02 | Spoofing | DELETE without session | mitigate | `requireAuth` already gates the route; handler keeps its 401 branch; client never calls DELETE for starters or guests |
| T-07-03 | Tampering | readHiddenStarters | mitigate | JSON parse in try/catch, result filtered through `isStarterId`, so a forged value can only hide built-in starters on that browser |
| T-07-04 | Repudiation | sound deletes | accept | Personal preference data, no audit trail needed at ASVS L1 |
| T-07-05 | Information disclosure | repro screenshots | accept | Throwaway accounts only, saved to the session scratchpad, not the repo |
</threat_model>
